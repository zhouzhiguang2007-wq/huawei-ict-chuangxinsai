# 碎片时间旅行推荐

把临时空档转换为可执行的微行程。核心标准不是“附近”，而是候选活动能够到达、完成，并在安全缓冲前返回下一项固定安排。

## 确定时间边界

先取得：当前时间、起点、最晚返回时间、返回地点，以及不可迟到的下一项安排。沿用已确认的行程日期、预算、天数和偏好；缺少影响判断的事实时每轮只问一个问题，不用典型游玩时长或默认预算替用户作答。位置只能来自用户主动提供、既有行程或本次明确授权的定位结果；未获得授权时询问起点，不调用或推断设备位置。

根据用户场景设置明确的安全缓冲，记录数值和理由。交通不确定、天气恶劣、带儿童或老人、赶车赶飞机时应扩大缓冲；不得为了让候选通过而压缩缓冲。

另外估算从收到建议到真正出发所需的准备时间，例如收拾物品、离店、下楼或等待同行者，并写入 `departure_preparation_minutes`。不得把当前时间直接当成实际出发时间，除非用户已在路上且能够立即行动。

缺少起点、返回期限或返回地点时先追问。若用户没有硬性返回安排，可询问愿意使用多长时间，并将该时间作为窗口而不是伪造截止点。

## 查询候选事实

使用已接入的地图 MCP、天气工具、官方资料或业务插件查询：

- 候选地点、类别和与用户偏好的匹配度；
- 当前时段的去程和返程路线状态、耗时、POI ID 与查询时间，必要时考虑不同交通方式；
- 营业和停止入场时间、预约或余量状态；
- 排队或入场耗时、最低有意义游玩时间；
- 天气适配、无障碍、体力和预算条件。

优先保留少量高相关候选，不为凑数量推荐低质量地点。真实信息保留来源和查询时间；模型记忆不能充当当前开放、路线或天气证据。外部来源缺失时标记未知，不假装已验证。

## 计算可行性

将候选整理为 [输入输出契约](references/input-output-schema.md) 的 `pocket_json`。运行 `scripts/evaluate_time_pocket.py`，或把其中 `main(args)` 放入 AgentArts 代码节点。

必须计入：

```text
总占用 = 出发准备 + 去程 + 等待/排队 + 最低游玩时间 + 返程 + 安全缓冲
```

同时检查活动必须落在有效开放窗口且不晚于停止入场时间。不能只用直线距离、平均车程或“看起来来得及”判断。不同地点间出现零分钟路线、路线不可用、查询时间缺失或数据过期时，必须重新查询或降级为 `incomplete`。脚本未实际运行时，不得声称代码校验通过。

- `feasible`：时间、开放和可用状态均有依据且通过；
- `incomplete`：数学上可能来得及，但路线新鲜度、开放或可用状态等关键事实未知；
- `infeasible`：已知条件下无法按时安全返回，或地点明确不可用。

## 选择与解释

只从 `feasible` 候选中给出主推荐。综合用户兴趣、时间余量、天气、体力、费用和体验独特性排序，不把“剩余时间最多”当成唯一标准。

输出一条主推荐和最多两条真正可行的备选，并解释：

- 为什么适合当前空档；
- 预计出发、到达、游玩结束和返回时间；
- 预留多少安全缓冲；
- 为什么没有选择其他看似热门的候选；
- 哪些事实是实时查询，哪些仍是估算。

没有完整验证的候选只能放入待确认项，不能标记为稳妥推荐。所有候选均不可行时，明确建议休息、就近用餐或提前前往下一安排；不要强行推荐。

## 与其他流程衔接

本技能只添加当前空档内的可选活动，不覆盖后续正式行程。用户确认后，由工作流把微行程作为临时段落写入当前计划。

若延误、闭园或天气已导致原行程冲突，应转入 `travel-replanner`；微行程生成后仍可交给 `travel-plan-review` 做全局复检。涉及购票、预约、支付或取消时仅提示用户确认，不代替用户执行。

## 输出

工作流模式返回 `status`、面向用户的 `message` 和机器可读的 `result_json`，具体结构见 [输入输出契约](references/input-output-schema.md)。不要在 JSON 外添加 Markdown 或代码围栏。

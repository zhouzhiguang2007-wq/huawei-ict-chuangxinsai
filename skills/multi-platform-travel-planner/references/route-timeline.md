# 完整线路与丰富行程报告

完整旅行报告应让读者沿着时间线从当天起点走到终点，知道**何时出发、怎么转场、每处玩多久、具体看什么、何时吃饭休息、几点回到哪里**。景点清单或“上午 A、下午 B”的概括只能作为摘要，不能代替逐日行程。

## 先算路线，再写文案

1. 以用户确认的出发日期、天数、出发地、到达/离开时间及住宿点为边界，生成每一个旅行日期。未确认的核心条件先逐轮询问；不得为了填满时间轴自行设定抵达时间或返程班次。
2. 按片区、营业时段、预约窗口、天气可用时段和用餐地点排景点顺序。把必去地点放入适合的时段，再取舍可选点；偏远点要写明往返时间和它挤占的活动。
3. 为每一段记录开始、结束、地点；跨地点必须插入交通段，写明起终点、方式、地图或运营方依据、车程/步行/换乘与候车。入场排队、取票、安检、集合点名、行李、入住、用餐及休息都占用真实时间。
4. 从已知锚点顺推：`下一段开始 ≥ 上一段结束 + 转场 + 候车/入场 + 必要缓冲`。景点游玩时长取 `离开时间 - 开始游览时间`，以官方建议、场地规模、用户节奏或有标注的规划估算说明依据。不要把排队、车程或团体集合算作游玩。
5. 首日从实际集合/抵达后开始，末日在返程集合、安检/检票或硬截止前到达。连续多日还要接上前一天住宿点与次日出发点；夜间跨城交通单独列段，不让“第二天到达”凭空出现。
6. 审查营业、预约、演出场次、日照、天气、步行强度和总预算。多人团体须预留上下车、点名、如厕和分组集合时间；长者/儿童的休息按已知需要安排，不猜测个人体力指标。

时间不能确定时保留时间窗和“待核实”原因，给出会影响哪些后续节点；不能编造精确分钟以取得形式上的完整。酒店或上下客点尚未定时，用明确的候选片区作条件性锚点，报告与校验结果都标 `incomplete`。

跨城铁路是当日时间线的硬锚点。已知日期、起终点和时间窗时，先自动尝试官方 12306 查询，再排依赖车次的退房、进站和返程活动。官方车次未查到或工具不可用时，不写“13:00–14:00 高铁返程”一类看似确定的时段；以“返程车次与到站时间待核实”占位，并把受影响的活动、预算和返程可行性标为 `incomplete`。不能让结构校验通过代替列车资料核实。

## 报告的逐日交付形态

每天先用一行说明“起点 → 片区及主要景点 → 终点、当天游玩与交通总时长”。随后给**逐段时间线**，至少包含：

| 时段 | 节点或转场 | 地点与方式 | 实际游玩/用餐/休息分钟 | 当场做什么与为何值得去 | 费用、预约和依据 |
|---|---|---|---:|---|---|

- 逐段列集合/出发、交通、景点游览、用餐、休息、入住或返程；不把半天塞在一个笼统格子里。每段标出开始和结束，转场标出出发地、抵达地和耗时。跨景点路径与“交通查询与接驳”表应一致。
- 每个主要景点写一个简短但具体的现场段落：安排它的理由、至少两项可辨认的看点或活动、建议的体验顺序、建议停留多久、预约/开放或天气约束；有拍照需求时写具体地标与推荐角度并交给拍照 Skill。引用能支持事实的资料，个人建议和估算需明确标记。
- 每餐写明餐饮片区或已核实餐厅、所占时段、推荐当地菜品与团体就餐条件；休息与自由活动也要有地点和时段。不要以未经核实的网红店、演出时刻或菜单填充篇幅。
- 每天结尾给可操作的替代：哪个节点遇到雨/闭园/满员会换成哪个**邻近且仍在开放时段**的地点，换后转场和费用如何变化。不能只写“雨天改室内”。
- 用 2–4 句解释当天节奏、景点间为何这样排序、拍照或美食重点、团队或无障碍注意点。丰富来自真实可做的细节，而非形容词和重复景点介绍。

报告总览、平台对比、预算与照片页可以另排版，但不能压缩掉逐日时间线。手机手册或 PDF 应复用**同一版**路线、地点编号、时间和费用。

## 结构化校验与交接

正式报告先保存与报告一致的时间线 JSON，并运行 `python scripts/validate_route_timeline.py <时间线.json>`。输入顶层为：

- `trip`: 已确认的 `start_date`、`end_date`、`days`，以及整段旅行的 `start_place_id` 和 `end_place_id`。
- `daily_routes[]`: 每天的 `date`、`start_anchor`、`end_anchor` 和按时间排序的 `segments[]`。锚点为 `{at, place_id}`，`at` 用带时区的 ISO 时间。
- 每个 segment 有唯一 `id`、`kind`、`start`、`end`。`kind` 可为 `gather`、`transfer`、`visit`、`meal`、`rest`、`check_in`、`check_out`、`free_time`、`other`。非交通段用 `place_id`；交通段用 `from_place_id`、`to_place_id`、`mode`。游览段再给 `visit_minutes` 和至少两条具体 `highlights`。未知值写 `null`，不填零。

校验器检查日期是否齐全、起终锚点、地点链、时间顺序与冲突、游览分钟数、未解释的长空档及连续日期的衔接。它不能证明地图时长、开放/演出、推荐内容或价格真实。针对这些事实，保留来源、查询时间与人工判断，并把计划适配到 `travel-plan-review` 的活动/legs 契约做时间、营业、预约和预算复检。

默认单个未说明空档不得超过 15 分钟、全天累计不得超过 30 分钟；如有候车、排队、休息或自由活动，直接列为对应时间段。只有用户的实际行程需要时才调整 JSON 中的 `max_unexplained_gap_minutes` 和 `max_daily_unexplained_gap_minutes`，并在报告说明理由，不得为让检查通过而随意放宽。

若校验器返回 `fail`，先修改路线再生成最终报告；`incomplete` 时明确列出阻断的地点、时间或资料，以及需要何时复核，报告只能是条件性草案。程序未实际运行时不得写“已通过校验”。最后人工核对：每个日期均有完整线路、主要景点的介绍不是空泛介绍、所有转场与费用表相符，替代线路也重新计算时间与预算。

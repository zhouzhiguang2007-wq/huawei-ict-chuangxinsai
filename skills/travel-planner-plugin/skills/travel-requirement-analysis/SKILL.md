# 旅游需求分析

把用户说法转换为可执行的旅行约束。只收集和规范需求，不查询景点、天气、路线或价格，不生成完整行程。

## 分析流程

1. 合并本轮输入与有效对话上下文。新陈述只覆盖用户明确修改的字段，保留其他已确认字段。
2. 区分用户事实、可安全推导值和未知值。不得把常见偏好当成用户偏好，不得推断当前位置。
3. 规范城市、日期、天数、人数、预算、兴趣、节奏、交通偏好、必去项和硬约束。完整字段定义及就绪规则见 [输入输出契约](references/input-output-schema.md)。
4. 校验日期与天数、人数明细与总人数、预算范围等内部一致性。可运行 `scripts/validate_requirements.py` 检查结构化结果；未实际运行时不得声称代码校验通过。
5. 完整旅游规划采用逐轮访谈：每轮只问**一个**当前缺失的问题，等待用户回答，再问下一项。优先顺序为目的地、出发日期或日期窗口、预算金额及口径、游玩天数、人数（涉及团费/住宿时）、兴趣与节奏；用户一次回答多项时全部记录，跳过已回答项。不得自行补出三天两晚、出发日期、预算或用户喜好。
6. 用户已在本轮或有效上下文明确给出的数值直接复用，不为完成提问流程而重复问。像“想拍照”“重点吃美食”可以形成**待确认偏好**，下一轮用具体选择问用户是否正确；不能把推测当成已确认事实。用户说“没特别偏好”也要记录，不反复追问。
7. 按输入输出契约返回结果。工作流模式只输出 JSON，不附加 Markdown、解释性前缀或代码围栏。

## 追问原则

完整规划的最低条件是目的地、出发日期或明确日期窗口、预算金额与口径、游玩天数。住宿、团费还需要人数与房间需求。缺少一项就逐轮询问，不把示例日期或过去的其他城市行程带入当前行程。

用户明确说“未设上限”时记录为无限额偏好；“经济型”等模糊说法仍要追问大概金额或区间，才能做预算报告。预算口径必须区分每人、全团或每天。

相对日期仅在宿主提供可信当前日期与时区时换算，并在 `derived_fields` 记录依据；否则追问具体日期。日期与天数冲突时不擅自选择其一。

地点偏好可以为空。`spot_a` 和 `spot_b` 仅用于兼容现有基础工作流：优先填用户明确给出的前两个必去地点，不足时使用空字符串，绝不编造景点。

交通方式未指定时输出 `unspecified`，不能默认步行。用户授权使用当前位置之前，不调用定位，也不把设备、IP 或历史地点当作出发点。

## 就绪判断

- `ready=true`：已具备当前任务所需的关键条件，且不存在未解决的硬冲突；完整行程还须有日期、预算口径、天数、人数。
- `ready=false`：关键字段缺失、相互矛盾，或当前任务要求的预算/人数口径不明确。
- `question`：`ready=true` 时为空字符串；否则是一条简洁的合并追问。
- 核心信息齐后再问一轮兴趣与节奏；有证据的偏好推断需用户确认，不能静默落地。用户明确无偏好时可结束访谈，不无限追问；其他未知值保留为 `null`、空数组或 `unspecified`，并列入 `unknown_fields`。

若用户只是随意咨询而不是要求制定行程，可输出已识别需求但保持 `ready=false`，在问题中询问是否开始规划。

## 输出与衔接

详细结构、AgentArts 标量输出映射和样例见 [输入输出契约](references/input-output-schema.md)。`requirements_json` 必须是完整需求对象序列化后的 JSON 字符串，供 `travel-planner`、住宿建议、行程校验和动态重规划复用。

本技能独立结束于需求结果，不自动调用其他 Skill。由 AgentArts 工作流根据 `ready` 决定：

- `false`：返回 `question` 给用户继续补充；
- `true`：查询真实 POI、路线、天气和开放信息，再把 `requirements_json` 交给规划器。

真实数据必须来自相应 MCP、插件或官方资料；本技能不能用模型记忆填充实时事实。

## 边界

不预订、付款、改签或取消；不保存证件和支付信息；非必要时不收集精确住址。用户主动提供敏感信息时，只提取规划所需的最小内容，不在结果中重复无关信息。
